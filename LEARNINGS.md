# Learnings

Tricks that made clifv's Lean proofs and builds faster, lighter or more robust, with the measured effect.
Add an entry when a change you made shows a measurable gain (or a measurable regression worth avoiding).
Keep each entry short: the problem, the trick, the numbers, where it is used.

None of these weaken what is proven: every compiler theorem still prints only `propext`,
`Classical.choice` and `Quot.sound`, and the kernel checks every proof.

## Kernel evaluation (`decide +kernel`, `rfl`)

### Scan Lists, not Arrays, in kernel-evaluated code
- **Problem:** `Array` combinators (`find?`, `foldl`, …) are well-founded recursive. The kernel evaluates them very slowly. Every Stock module that runs `Stock.lower` under `decide +kernel` looked up `"lower"` in the 2,483-term ISLE program with `Array.find?`.
- **Trick:** define the lookup as a `List` scan and add an `@[csimp]` theorem that swaps the `Array` version back in for compiled code, so runtime is unchanged.
- **Effect:** a 700-element scan went from 4.3 GB / 17–30 s to 0.48 GB / 0.25 s; `program.termByName? "lower"` from 4.65 GB / 17 s to 0.79 GB / 2.6 s (BuildDiet, `FV/Isle/Syntax.lean`; branch `agent/build-diet-syntax`, not merged: `Syntax` is in the `FV.Opt.Proof` cone, so it rebuilds every rule module, e.g. `RuleShifts3P2` ~7,700 s / 8 GB cold; its Opt impact must be measured first).

- **Same for `Array.map`/`mapIdx`:** the regalloc checker's `AState` (an `Array` of ~140 location sets) used `Array.map`, `mapIdx` and an indexed `List.range` scan; the kernel runs `Array.mapM`'s index loop with one `List.get` walk and one `List.concat` per element (quadratic). Microbenchmark, 20 `remove`s over a 300-location state in `decide +kernel`: 7.96 GB / 27 s with `Array.map`, 0.56 GB / <1 s with `⟨a.toList.map f⟩`. `FV/Backend/RegallocCheck.lean` now specifies `remove`/`meet`/`parCopy`/`le`/`forgetDefs`/`forgetOps` by `List` recursion, `@[csimp]` keeps the `Array` code, `*_eq` give proofs the old forms (BuildDiet). Scheduler build, main gate `bdb71827` → this branch (peak: maxrss → cgroup peak): `PerEdgeSpillEntryFixture` 388 s / 14.7 GB → 86 s / 8.9 GB, `StockPerEdgeAllocatorWitness` 123 s / 11.7 GB → 65 s / 7.7 GB, `StockPerEdgeCriticalAllocatorWitness` 109 s / 14.2 GB → 120 s / 9.1 GB; with the single certificate below, `PerEdgeSpillCycleFixture` 1,708 s / 17.8 GB → 73 s / 9.3 GB. The machine-wide largest peak dropped from 17.8 GB to 11.9 GB (`StockSourceSinkTable`).

### Prefer structural recursion to well-founded recursion
- **Problem:** the kernel cannot reduce well-founded definitions efficiently (or at all, in practice). `fitsCl`/`fitsTy` in `DefGenDom` used well-founded recursion, and every `decide +kernel` check over them failed.
- **Trick:** rewrite them with structural recursion (fuel or the list itself), with the same equations.
- **Effect:** the failing `DefGen` certificates now pass (T6).

### Evaluate a concrete pipeline once per certificate
- **Problem:** `PerEdgeSpillCycleFixture` checked seven facts about one `Stock.lower`/`prepareAt`/`allocResultAt`/`lowerRFunc` run with seven separate `decide +kernel` theorems; each re-ran the whole pipeline (`Stock.lower` alone 8 GB / 21 s, with allocation 18 GB / 58 s).
- **Trick:** one `decide +kernel` over the conjunction (the evm.fast-dev "remove repeated work" idea; kernel-opaque `boxedValue` caches would be the next step if one evaluation were still too much).
- **Effect:** 18.2 GB / 748 s → 18.1 GB / 66 s, same statement (BuildDiet, before the `AState` change; with it, 9.3 GB / 73 s). Splitting certificates lowers the peak only when the parts do not share the expensive evaluation.

### `subst_vars` rescans: `whnfR` instead of `whnf` of the equation sides
- **Problem:** `Lean.Meta.substVars` substitutes one variable per scan and restarts; each scan `whnf`s both sides of every equation at default transparency. In the isel inversion proofs (`isel_inv`, `ctl_inv`, `isel_destruct; subst_vars`) the contexts hold many equations between big interpreter terms, so `subst_vars` was ~95% of the time (`IselCtlTry`: 1,420 s in one call).
- **Trick:** `FV/Backend/Proof/FastSubst.lean` (imported by the isel hub `IselCmpBase`; `macro_rules` makes every `subst_vars` use it) copies `substVars`/`subst`/`substEq` with the same scan order, choices and hypothesis handling, and changes only `whnf` → `whnfR` of the sides (`(a, b).1 = x` still reduces). An exact copy matters: a version that walked the equations in its own order and replaced hypotheses in place changed `rename_i` order and broke `IselFamAluBShiftTerms` and `StockCmpSelectedCalls`. Dead ends: a purely syntactic pass breaks `IselCmpIcmp`, and a syntactic pass followed by one stock pass has no gain (812 vs 838 s).
- **Effect** (BuildDiet): `IselCtlTry` standalone, same session: 838 s → 28 s (2.0 GB both); `IselCmpIcmp` 228 → 195 s. Scheduler build, main gate `bdb71827` → branch: `KillTryDefs` 1,295 → 23 s, `IselSzCall` 1,340 → 18 s, `LinkOwnCallsTry` 1,388 → 17 s, `LinkOwnCallsStmt` 435 → 10 s, `IselShpCall` 331 → 13 s; also `IselShpTry` 17 s, `IselTermFactsCall` 25 s, `IselCtlTryInd` 14 s (they were 1,700–1,800 s standalone before).

### Avoid `rfl`-based simp steps on big concrete terms
- **Problem:** `StockCmpWithFlags` elaborated in 1.9 GB, but the kernel needed 23 GB to re-check one `simp` step of `isel_eval`: monad-law lemmas proved by `rfl`, applied to a large concrete state.
- **Trick:** use copies of the monad laws proved by `rw` instead of `rfl` (a local `isel_eval_k`).
- **Effect:** 23.6 GB / 128 s → 2.1 GB / 21 s (branch `agent/build-diet`, being merged). The same change did not help three other heavy Stock modules, so measure before changing a shared tactic.

### Never reduce the whole generated program in the kernel
- **Trick:** compute table properties with an untrusted generator that writes literal data, then check the data with small leaf-wise `decide +kernel` certificates (e.g. `TermSetData.lean` + `KillTab.lean`, `IselPrgTab.lean`). Split each conjunction and check one entry per leaf.
- **Why:** whole-table `decide`/`native_decide` hit 20+ GB or needed compiled evaluation. Leaf-wise checks stay small and need no extra axioms (T6 removed every `native_decide` from the compiler theorems this way).
- **Cost (measured 2026-10-22, `LEAN_NUM_THREADS=2`):** the per-entry `chkEntry` certificates of the ISLE progress tables are the slowest leaf-wise checks: `IselPrgTab` (V7, ~1000 entries) 3100 s at 5.0 GB, `IselPrgTabT` (typed scope, 1090 entries) 68.6 min. The time is the sum of the entries' kernel checks (each one already its own leaf), so smaller chunks do not shorten it; keep their imports narrow so they rebuild rarely (S11 FloatProg).

### Split one leaf further: chunk its environments
- **Problem:** one leaf of the typed coverage table (`stmtOkT rule_lower_2267`, a `select` rule on the integer-`select` family) has 256 pattern environments; its single `decide +kernel` was killed at 8, 16 and 22 GB, while its 30 other families take ~1 s together. Kernel memory grows with the environments checked in one `decide` (32 environments: 4.7 GB incl. 2.8 GB of imports).
- **Trick:** prove the leaf from `envOkT` checks of 32-environment chunks (`(envs.drop (c*32)).take 32`) plus `isSome`/length certificates, glued by a small `all_of_chunks` lemma; find such leaves by `decide +kernel`-probing each rule and family separately under a memory cap. The generator (`IselCovTGen.heavy`) emits this for the listed rule/family pairs.
- **Effect:** `IselCovTTabS30` builds in 119 s at 4.5 GB (was: killed at 22 GB).
- **The chunk size is per leaf, not per table:** the typed emission table (`IselEmitTGen.heavy`, rule/family/chunk triples) reuses 32 for rule 2267, but its vector-lane rules 1222-1228 on family 2 (64 environments) cost 8 GB per 16 environments under the emission check; with 8 per chunk `IselEmitTTabS5` builds in 509 s at 5.1 GB (was: killed at 22 GB). Probe a leaf's chunk before picking the size.
- **Cost tables: chunk entries too, and one entry per `decide`:** the typed cost tables (`IselSzTGen`) ran out of memory in 4 of 26 entry modules (C18 killed at 9.2 GB). Term 575's 24 entries go through ~4040 abstract environments each: each such entry is now proven rule by rule via `cRuleLe_of_chunks` from `decide`s of 128 environments, packed ~1024 environments per module (`IselSzTTabH*`, 240 modules, ≤4.4 GB, mostly 2.3 GB). Separately, 8 cheap entries (<50 environments each) per `decide` still took 8.1 GB / 282 s in one declaration: the environment count does not predict the kernel's cost, so every entry gets its own `decide` (C modules 7.7 GB → ≤1.8 GB).

### `assumption` at reducible transparency
- **Problem:** after `ArmState` gained a field, `stlxr_congr` in `LoopRun.lean` ran out of heartbeats even at 8M: `assumption` was unfolding the state structure.
- **Trick:** run the tactic's `assumption` with reducible transparency.
- **Effect:** the file compiles in about 30 s.
- **Again in `RegallocAtomic`:** `sw_tac_c`'s `assumption` and `refine SameWorld.w_left/w_right/w_both'` fail on `SameWorld F (write_mem_bytes 8 a (x.cast h) s) (write_mem_bytes 8 a x …)` only after unfolding `write_mem_bytes` into `ArmState` literals (each projection ~616k times), before `sw_wmb_cast` applies; the cost is exponential in the byte count (4 bytes: 11 M heartbeats). With those alternatives at reducible transparency, `corr_storeRelease` 33.2 G → 0.39 G heartbeats for the module; `RegallocAtomic` 815 s / 8.3 GB (record) → 16 s / 0.4 GB (workstation).

### No `first | exact a | exact b …` over goals mentioning a big definition
- **Problem:** in `synthTable_le` (`FV/Link/Ld/RelocTotal.lean`), `first | exact a | exact b …` over goals that mention lean-ld's planner `layPre o st g` ran out of heartbeats (over 200000): each failed `exact` tried to unify by unfolding the whole planner.
- **Trick:** one explicit tactic per goal (the right lemma named for each case), no `first` fallback chain.
- **Effect:** the file checks in about 9 s (A1c, #409).

## Proof search (`kbv`)

### Close recurring goal shapes before the general `kbv` search
- **Problem:** `kbv` tries about 20 methods in order, each under its own heartbeat budget. A goal shape that only a late method closes pays for every earlier failure, and a rule proof can produce hundreds of such goals (one per type combination). `RuleShifts3P2` (`shifts.isle:50`) was 1.8 h of the 2.3 h cold-build critical path: `kbv_amt` closed all 684 `kbv` goals of `shifts_71` in 14 s, but not the goals `sshr (ishl (uextend x) k) k = sextend x` (`k = wide - narrow`) of `shifts_50`, so each of those went to the general search (1–8 s; the first 95: 345 s). `RuleShifts3P1` (`shifts_41`): `(x <<< k) >>> k = x &&& allOnes >>> k`, 1–38 s each. `RuleShifts2P1` (`shifts_319`): `(y &&& x <<< k) >>> k = x &&& y >>> k`, the same identities under CLIF's `ishl`/`ushr`, and `(allOnes).sshiftRight k = allOnes`, up to 75 s each. The imm64 rotation specs (`RuleRestEmbedRotl`/`Rotr`): `kbv_modsplit` closes every case, but only after `kbv_split` and others fail (10–12 s each).
- **Trick:** find which goal shapes reach the general search: a scratch copy of the module with an `elab_rules` for `kbv` that logs `KernelBV.bvStatement` of each goal, which method closed it, and the time. Then add the one identity the shape needs to the module's first-try method (`kbv_amt` in `RuleInfraShiftAmt.lean`: `sshr_shl_setWidth_top`, `shl_shr_of`, `and_shl_shr_of`, `shl_or_shl_of`, `allOnes_sshiftRight`, with CLIF `ishl`/`ushr`/`sshr` unfolded), or try the method that works first (a `local elab_rules` with `kbv_modsplit` in `RuleRestEmbedRotl`/`Rotr`). A failure still falls through to the general search. For the specs, also split on widths instead of types (`imm_wcases`, `RuleRestEmbedBase.lean`): `f32`/`f64` repeat the `i32`/`i64` goals, so there are 16 cases instead of 36.
- **Effect** (this workstation, `LEAN_NUM_THREADS=2`; origin/main by `lake env lean` → the branch in the `lake-serial-build.py` run): `RuleShifts3P2` 4,541 s / 7.1 GB → 152 s / 4.3 GB, `RuleShifts3P1` 1,993 s / 9.8 GB → 170 s / 3.6 GB, `RuleShifts2P1` 821 s / 5.8 GB → 178 s / 4.6 GB, `RuleRestEmbedRotl` 1,145 s / 8.3 GB → 461 s / 4.1 GB, `RuleRestEmbedRotr` 988 s / 8.3 GB → 418 s / 4.1 GB. The other `kbv_amt` modules are unchanged or a little faster. Statements are unchanged. The cold-build critical path (recorded seconds) went from 2.31 h to 1.69 h, and it now runs through the backend.
- **A module that never opted in:** `RuleCprop3` (`cprop.isle` 320–324, reassociating shifts of constants) used the general search for its 252 goals per rule, `x <<< a <<< b = x <<< b <<< a` over value and amount types: 1 s each at 8 bits, 25 s at 16 bits and more at wider types. With the module-local `elab_rules` and `kbv_amt` collecting two shifts in one direction into one (`BitVec.shiftLeft_add`, `ushiftRight_ushiftRight`, `BitVec.sshiftRight_add`), each closes in ~50 ms (orb, scheduler builds at the same load: 6,575 s / 1.5 GB → 290 s / 1.3 GB). The other `kbv_amt` modules stayed within ±7%.
- **The same identity under every type split:** `RuleIcmp2` (`icmp.isle:84`, `select` of `uextend` of `icmp` as `select` of the `icmp`) split every `Ty`/`IntCC` variable before `kbv` and sent 2,940 goals, all `Sem.select (Sem.uextend w c) x y = Sem.select c x y` with `8 < w`, to the general search, where `kbv_bitsh` ran out of its budget on each before `kbv_split` closed it (93 G heartbeats, about an hour). A width-generic lemma (`select_uextend_of_lt`) tried before the split closes them: `ok_rule_icmp_84` 93.3 G → 0.42 G heartbeats; `RuleIcmp2` 1,344 s (record) → 431 s (workstation, `lake-serial-build.py`, loaded).
- **An identity outside the shifts modules:** `RuleArith5` (`arithmetic.isle` 610–612, `bxor` of two `ishl`/`ushr`/`sshr` by one amount) never opted into `kbv_amt`; its 49 goals per rule, `x <<< a ^^^ z <<< a = (x ^^^ z) <<< a` per value and amount type, went to the general search (`arithmetic_611`: up to 97 s per goal, 880 s in all). `kbv_amt` now collects two shifts by one amount under `^^^` (`shl_xor_shl_of`, `ushr_xor_ushr_of`, `sshr_xor_sshr_of`) and `RuleArith5` tries it first: 744 → 37 s (orb, alone); the other `kbv_amt` modules are unchanged (±2%, timed side by side).

### `kbv` searches do not count against `maxHeartbeats`
- **Problem:** `KernelBV.isolate` runs each search on its own budget and resets the heartbeat counter afterwards, so a proof stays under its `maxHeartbeats` however long its searches take: `ok_rule_icmp_84` was charged 2.6 G heartbeats for 93 G of work, and a slow rule proof does not show up as a heartbeat failure.
- **Trick:** `-Dkbv.reportHeartbeats=<N>` prints every search that used at least `N` thousand heartbeats to standard error (position, declaration, closed/failed). `N` around 10,000 catches the pattern of many medium searches (`icmp_84`: ~31 M each); `lake env lean -Dkbv.reportHeartbeats=10000 FV/Opt/Proof/RuleX.lean 2>&1 | grep '^kbv:'`.

## Forward evaluation (`opt_eval`)

### Normalise only the head computation; skip `rw` attempts that cannot match
- **Problem:** `opt_eval` evaluates a rule's right-hand side one interpreter step at a time: a `rw` with the first of ~50 equation lemmas that matches (`opt_unfold`), then `simp` passes over the whole hypothesis (`opt_norm`). The magic-number `div` sequences of `RuleSkeleton3`/`RuleSkeleton5` take ~500 steps per evaluation, and `RuleSkeleton5` evaluates four of them per theorem (per sign of the divisor and of the multiplier): ~180 s each on an orb, 85% of the module. A perf profile (`perf record --call-graph dwarf` on the `lean` process) showed 81% of the time under `Simp.simpLambda`: every pass re-traversed every pending continuation (`fun p => …` of a `bind`, with its unreduced `match`es), so a step cost 0.1 s at 1,800 objects and 0.7 s at 3,100. The failing `rw` attempts (a full `kabstract` each) were most of the rest.
- **Trick:** `opt_eval_head` (`FV/Opt/Proof/RuleInfraEval.lean`): a `simp` pre-procedure `opt_bind_head` simplifies only the first computation of a `bind` and reduces `Except.ok a >>= f` to `f a` (by definition, without visiting `f`); `opt_unfold_head` skips the equation lemmas whose left-hand-side head (with its number of arguments) is not the head of a closed subterm of the hypothesis, which `kabstract` could not match anyway, and tries the others in `opt_unfold`'s order. The skeleton `div` templates opt in (`skel_rhs_dc`, `sdc_eval`, `sdc_rhs`); other modules keep `opt_eval`. Dead end: a `@[congr]` lemma that freezes the continuation of `bind` made the evaluation twice as slow.
- **Effect** (orb, `LEAN_NUM_THREADS=2`, `lake-serial-build.py`; origin/main → branch): one `RuleSkeleton5` evaluation 180 → 30 s; `RuleSkeleton5` 4,516 s / 3.5 GB → 917 s / 3.0 GB, `RuleSkeleton3` 1,866 s / 5.9 GB → 358 s / 2.4 GB. Statements unchanged.
- **Also for helper evaluations:** `RuleIcmpComposeEval` proves 20 lookup lemmas (`intcc_class`, `decompose_intcc` per condition code) by stepping the interpreter with two `simp` calls per step, each run twice, over the whole hypothesis: 96% of the module. One `simp` call per step with `↓opt_bind_head`, and `opt_unfold_head`: 391 → 55 s (orb, alone).

### One `simp` call per `opt_norm`; no catch-all equation lemma in `opt_match`; no `whnf` in `rule_lhs`'s substitutions
- **Problem:** in most rule modules the time is in the `simp` calls of the template, not in `kbv`. Three costs recurred across modules (trace.profiler and leanprof, `RuleArith4`, `RuleShifts4`, `RuleIcmp1/2`, `RuleExtends2`): `opt_norm` alternated two `simp` calls (`opt_data`, then `opt_monad`/`opt_imm`) until neither applied, traversing the whole hypothesis on every call; `opt_match` unfolded `ArgsRel` by its equation lemmas, whose catch-all `ArgsRel.eq_3` (lists of different lengths) has side conditions that `simp` tried and failed to discharge on every unfolding (14–20% of `RuleArith4`/`RuleShifts4`); `subst_vars` in `rule_lhs` put both sides of every equation into `whnf`, including `hev`, the interpreter's evaluation, rescanning after each substitution (`ok_rule_icmp_41`: 48%). `opt_unfold` also tried ~50 equation lemmas by `rw` in turn.
- **Trick:** `opt_norm` (and `pow2_norm`) is one `simp only [opt_data, opt_monad, opt_imm, …]`; `opt_match` uses the four constructor cases of `ArgsRel` (`ArgsRel_nil_nil`, …, `RuleEmbed.lean`); `rule_lhs`/`rule_lhs_c` use `opt_subst_vars` (`RuleTactic.lean`, `subst_vars` with `whnfR` sides, the definitions of the backend's `FastSubst`); `opt_unfold` tries only the lemmas of functions that occur in the hypothesis (`optUnfoldEqns`, shared with `opt_unfold_head`).
- **Effect** (workstation, trace.profiler heartbeats, e14718a2 → branch): `RuleExtends2` 37.7 → 20.9 G (peak 16.6 → 14.0 GB), `RuleExtends` 16.5 → 8.3 G, `RuleIcmp1` 6.1 → 3.2 G, `RuleArith4` 4.5 → 2.3 G, `RuleCprop2` 4.2 → 2.1 G, `RuleSelects1` 10.7 → 8.0 G; `RuleSkeleton3/5` −5% (`opt_eval_head` had already removed most of their `opt_eval` cost). The `FV.Opt` modules built in both runs: 23,291 → 11,734 s (scheduler, loaded machine). Statements unchanged.

## Module structure and imports

### Don't import umbrella modules from hub files
- **Problem:** the generated `IselData.lean` imported the whole `FV.Backend` umbrella but used only `Isel`/`MInst`. Nearly every isel proof and every Stock module sat downstream of it.
- **Trick:** import only the modules actually used.
- **Effect:** a change to `Unwind`, `Regalloc`, `DeadCleanup`, … rebuilds about 330–445 modules instead of 1,630–1,690 (Stock: 1,116 → 78–112), about 12.3 h → 2 h of module time (#323).
- Similarly, `FV.Opt.Proof.*` no longer imports `FV.Backend` (#257), so backend changes don't rebuild the 317 rule modules. Don't add such imports back.

### Split heavy modules
- Lean builds one module per process and a module's peak is roughly its heaviest declarations together. Splitting a heavy file into parts (keeping the old module as a file that imports the parts, so importers don't change) lowers the peak and lets the parts build in parallel.
- **Effect** (standalone `lean`, same session, peak RSS before → heaviest part): `RuleBitops7` 19.3 → 6.1 GB, `RuleArith` 15.2 → 4.5 GB, `RuleRestEmbed` 15.8 → 8.6 GB, `RuleBitops2` 12.7 → 5.2 GB, `RuleBitops5` 11.0 → 6.3 GB, `RuleShifts2` 9.5 → 6.1 GB. `RuleShifts3` did not improve (the part with `shifts_41` alone is ~10 GB): splitting helps when the peak is several declarations together, not one big one. Statements unchanged (all 7,998 `FV.Opt` constants hash-identical). (BuildDiet, `FV/Opt/Proof/Rule*P<n>.lean`.)
- Don't over-split: evm.fast-dev found larger checkpoint groups built faster warm (see below).

### Don't depend on private library internals
- A proof that reached into the private internals of `Array.qsort` would break on a toolchain update. Sorting `cfg.loops.attach` instead carries the membership fact through the sort, with the same output (#318).

### Keep Mathlib out of the main import graph
- **Problem:** making `FV/Float` import FloatLib (which needs Mathlib) put 1,778 Mathlib modules upstream of 2,624 of 2,812 FV modules.
- **Numbers:** +1.4 GB peak memory per module (median of 222), +3–4 s import each; under load LegalArith 94 → 134 s, LegalShift 83 → 161 s; 8 breakages in the first 360 modules (`alias` is a keyword, Mathlib simp lemmas give "no goals"/unsolved goals), none on the same modules with the bare toolchain bump.
- **Trick:** a leaf Lake package (`float-spec/`) holds the Mathlib-dependent equality proofs; nothing imports it. Cost there: Mathlib cache ~1 GB download / 7.5 GB disk once, FloatLib ~2.5 min, FVFloatSpec ~1.5 min at ~2.6 GB per process (FloatBridge).
- **Don't bump the whole repo for one leaf's dependency:** FloatLib needs Lean v4.35.0. The repo-wide 4.34.1 → 4.35.0 bump reached only ~650 of 3,546 modules after 6 restarts, each stopped by new breakages (heartbeat limits on concrete `rfl`/`decide`, instance-transparency unification blocking `exec_bitfield` rewrites, a `kbv` budget), and would rebuild every branch and the shared cache (branch `agent/floatlib-lean435-only`, parked). Instead `float-spec/` has its own `lean-toolchain` (v4.35.0) and compiles the 5 core-only FV/Float modules from `../FV` into its own `.lake` (a `lean_lib` with `srcDir = ".."`, not `require fv from ".."`: a path dependency would build into the root's `.lake` and the shared cache). They compiled unchanged on 4.35.0 in under 1 s each; `float-spec/defs-hash.lean` checks both toolchains elaborate identical definitions (FloatBridge3).

## Build infrastructure

### Threads per Lean process don't help us
- Going from 2 to 8 threads gave no measurable gain on the slow modules: they spend their time in one declaration on one thread. Across 4,198 recorded module builds the median CPU/wall ratio was 1.01 (BuildAccel).
- **Exception:** `Elab.async` matters for `bv_decide`-heavy modules (`RuleExtends`: 1,652 s off vs 174–186 s on, at about twice the memory).

### Memory-cap every Lean process; share one Lake cache
- `scripts/memcap.sh` runs each command in a memory-capped cgroup (with a `/proc` watchdog fallback when the systemd user manager is down, #325). Without caps, one runaway `lean` triggered global OOM kills.
- `FV_LAKE_CACHE` points every worktree at one shared Lake artifact cache (hard links; same filesystem as the worktrees): a fresh worktree at a built commit needs no rebuild (#253).
- `scripts/lake-serial-build.py` builds module by module with caps from recorded peaks, runs light modules packed and heavy ones alone (#258).

### Ask Lake once which modules are out of date
- **Problem:** with the shared cache 90–97% of a full `FV FVTest` build was already built, but the scheduler still started one memcapped `lake build <M>` per module (1–3 s each under load, 6 at a time). A warm build at a fully cached commit (5a76867c, 3,138 modules, 0 to build) took 27.5 min wall and 925 CPU-s; the main gate's 0-built runs took 7.5–27.5 min with 12 jobs.
- **Trick:** one `lake build --no-build <all modules>` restores everything cached and lists the out-of-date modules (Lake stops there, so their dependents are checked the same way, in one batch, once their imports are built); only the listed modules get a `lake build <M>` (`scripts/lake-serial-build.py`, BuildInfra).
- **Numbers:** same warm commit: 27.5 min → 1.9 s (4 CPU-s; the check itself 0.7 s). A branch adding one theorem to `StockCmpZeroMatch` (58 modules to rebuild), both runs at the same time: 38.8 → 16.3 min wall, 1,520 → 1,048 CPU-s; 22 batch checks took 7 s in total.

### Don't build a module twice at the same time in two worktrees
- **Problem:** agents that rebase onto the same new main build the same modules at the same time; the cache only helps once one of them has finished.
- **Trick:** before building a module the scheduler takes an `flock` in `<cache>/.fv-inflight/`, keyed by a hash of the module's and its imports' sources, toolchain, lakefile and manifest; a scheduler that finds it held builds other modules meanwhile and, once the lock is free, runs `lake build <M>`, which restores the module from the cache. A crashed holder releases the lock automatically.
- **Numbers:** two worktrees building main at 5c1351a0 at the same time: 20 modules restored (1–2 s each) instead of built, about 3,900 s of compute saved (`StockAddSubExtensionWitness` alone 2,782 s at 9 GB).

### Record lean's peak from the cgroup; don't double the cap after a systemd-oomd kill
- **Problem:** the recorded peak was `/usr/bin/time`'s maxrss: lake's (0.1 GB) when lean was killed, lean's RSS including mmapped `.olean`s otherwise (e.g. 9.0 GB vs 7.3 GB counted by the cgroup). Every kill counted as "hit its cap" and was retried alone at twice the cap, but on 2026-10-22 systemd-oomd killed 237 clifv scopes for memory pressure on the whole user session (the kernel killed 97 at their own cap): `RuleShifts3P2` ran 66 min at 10 GB, was killed by oomd, and was retried from scratch at 20 GB.
- **Trick:** `scripts/memcap.sh` with `FV_MEMCAP_STATS=<file>` (set by the scheduler) writes the scope's `memory.peak` and `memory.events` `oom`/`oom_kill` when the command exits (`OOMPolicy=continue` keeps the scope alive when the kernel kills lean). `oom` > 0: own cap, retry at twice the cap; otherwise (no file: oomd stopped the whole scope; `journalctl -u systemd-oomd` names the unit) retry at the same cap, up to 3 times. The scheduler also starts nothing whose recorded peak does not fit under `clifv.slice`'s MemoryHigh minus 4 GB, so it queues instead of pushing the slice into the reclaim that makes oomd kill; waiting heavy modules queue machine-wide, oldest first (`/tmp/clifv-heavy-queue`).

### Read-only hard links in `.lake/build`
- **Problem:** restored outputs are hard links into the shared cache, mode 0444. When a module is built over them (two `lake build`s of one module in one worktree, e.g. a scheduler restarted while its old builds still ran, or a restore from the cache during a long build), lean fails at the end with `permission denied (error code: 13)` on the `.ilean`/`.c` (10 such failures in scheduler logs on 2026-10-22, after builds of up to 8 min). The read-only mode protects the cache: nothing is written through the link.
- **Trick:** the scheduler unlinks a module's read-only outputs before building it when the batch check says it is out of date, and on that error unlinks the named module's read-only outputs and retries once. It also stops its running builds when it is stopped (own process group; SIGTERM/Ctrl-C), so a restarted scheduler never races its predecessor. Reproduced (a read-only link put in place during the build): one failure, unlink, then built; the linked file was left unchanged.

### Wrapper tools don't make cold builds faster
- [turbo-lean](https://github.com/Th0rgal/turbo-lean) is not a Lean build: `turbo-lean build` runs the project's own `lake build` and caches the outputs. Its fast paths are cache hits and per-theorem checks against `sorry`-stubbed prefixes, which a gate cannot accept.
- Measured on 7 heavy modules, run at the same time with the same caps: +4.1% wall, +1.4% CPU (a fixed ~35–50 s per call for hashing and ingest), same peak RSS, identical statements and axioms for all 22,322 constants. Not adopted (TurboLean, `docs/research/turbo-lean.md`). Our cost is kernel checking of single large declarations; only proof changes reduce it.

### Iterate on one theorem with `turbo-lean check --decl`, not a module rebuild
- **Problem:** to re-check one edited proof in a heavy module, an agent rebuilds the whole module: KillTab 1,697 s, IselShpTry 1,658 s, IselCtlTry 952 s.
- **Trick:** `turbo-lean check FILE --decl THM` elaborates the file prefix with the earlier theorems as `sorry`, in a warm worker. Measured: first check 1.3–5 s, an edit 0.04–1.3 s, the same verdicts as Lean on broken proofs, scope peak ≤4.5 GB. It gives no speedup when the edited theorem is the expensive one (KillTab `tabOkB_S`: 788 s) and it rejects `native_decide`. Only for the dev loop; merges keep lake + audits. Usage: `docs/USAGE.md` "Fast proof-edit loop"; details: `docs/research/turbo-lean.md` (TurboTrial2).

### Linter warnings put the worktree path into the `.olean`
- **Problem:** `IselTermFactsCall` and `IselCtlTry` gave different `.olean` bytes on every build (three builds, three hashes; TurboLean). Rebuilding `IselTermFactsCall` outside the cache therefore rebuilt 30 downstream modules, including `KillTab` (~1,930 s).
- **Cause:** not nondeterminism but the source path. Lean 4.34 stores every linter warning in the `.olean` (`lintLogExt`, `Lean/Linter/PersistentLintLog.lean`, for `lake lint`) together with the file name Lake passed, which is absolute. In one worktree the bytes are identical (9 builds of the two modules: plain `lean` with 1, 2 and 8 threads, `lake build` twice); in another worktree they differ. 337 of 1,922 `FV` `.olean`s contained a worktree path (linters `unusedSimpArgs` 1,250 warnings, `unusedVariables` 157, `unnecessarySimpa`, `unusedSectionVars`, `defProp`, `constructorNameAsVariable`). When several agents rebuild the same module at once (e.g. after a shared change), each gets its own bytes and all their dependents miss the shared cache.
- **Fix:** `lakefile.toml` `weakLeanArgs` turns those six linters off for builds only. `weakLeanArgs` is not part of the module trace, so nothing rebuilt and cached modules stay valid; the editor still shows the warnings. Rebuilt `IselCtlTry`: no path in the `.olean` (BuildDiet).

### Merge first, verify on main
- When main moves faster than a full rebuild, a branch that passed its full checks on a recent main and rebases cleanly needs only a targeted build; a continuous main gate runs the full list afterwards and failures are fixed forward. A wrong merge can make main fail to build; it cannot make a false theorem pass, because the kernel checks every proof.

### Batch ready branches into one gate run (merge train)
- **Problem:** every PR author ran a full `FV FVTest` scheduler build plus the run-time gates, and the main gate repeated it per merged commit; with ~12 agents merging, the heavy lock serialised these runs (one main-gate run on `8b127ab0`, after a mid-level change: 277 min).
- **Trick:** authors build only their changed modules and importers; MergeTrain merges every ready branch onto origin/main locally, runs `scripts/main-gate.sh run` once on that train, then squash-merges the PRs in order (stacked PRs rebased onto the previous squash) and checks that main's tree equals the train's. Real conflicts (shared registries such as `closure.rs`/`Closure.lean`/rcases arms) are dropped from the batch and composed separately.
- **Effect (2026-10-23):** batch 1: 17 PRs in one gate run, 170 min wall (scheduler 3306/3306, 1100 built, 161 min, mostly `LowerSimT` dependents; the tail of exes, crate-proofs, 66 audit files and run-time gates: 9 min). Batch 2: 3 PRs in one run, 16 min (68 built, 10 min; tail 5 min). Gated separately, the `LowerSimT` rebuild is paid once either way, but every other PR needs its own run on the heavy lock: batch 2's 16 min (a warm run with a small change) is the measured lower bound per run, so ≈16 × 16 min ≈ 4.3 h saved for batch 1 and ≈ 2 × 16 min ≈ 0.5 h for batch 2 (estimate from these measured runs).
- **Batch 13 (2026-10-27):** squash only while main's tree stays equal to a gated train tip; a mid-sequence squash conflict (stacked chains after earlier squashes, main moving in between) left main half-merged and red for ~1.5 h until a remainder PR (#638) was re-gated. On a conflict, stop, recompose the remaining PRs on the new main and re-gate before merging more.

## Compiled checkers (`lean-link`, `link-check`)

### Hash maps behind a lookup parameter, not `List.lookup`/`P.func?` per element
- **Problem:** `lean-link --verified` took 2 h 26 min on fv-demo with std in the program (28,550 functions, 25,868 data objects; T3, `docs/plans/std.md` §2.2). gdb stack sampling (no `perf` on the machine) showed list scans repeated per element: `P.func?` (a scan of `P`) at every declaration/call site in `progScopeB`, `List.lookup` of the image symbols per (function, function) pair in `indB`, `reachSet` making `|data| + 1` passes over all data objects, a membership test against each unit's `localNames` list per name, `symTable` rebuilt per outside name.
- **Trick:** keep the checked definitions, add a variant taking the lookup as a function (`progScopeWithB F`, `= progScopeB` at `F = P.func?` by `rfl`), build a `Std.HashMap` once (`funcMap`, `assocMap`) and prove `(funcMap P)[n]? = P.func? n` / `(assocMap l)[n]? = l.lookup n` (foldr of `insert`, `HashMap.getElem?_insert`); the evaluated `inScopeInPar` uses the hash-map variant and `inScopeInPar_eq` stays a `simp` proof. Worklists instead of fixpoint passes; hoist tables out of `filterMap`.
- **Numbers:** `lean-link` 2 h 26 min → 11 min 55 s (715 s, max RSS 2.3 GB), no statement changed (`FV/E2E/LinkScopeFast.lean`, `FV/Front/Bundle.lean`).

### Classify once per section, not per relocation; sum sizes once
- **Problem:** `lean-link --ld` deciding `compileExe_total_ldIn`'s premises took 12–122 s per survey/fv-demo executable (A1, #409). Per-check timing (`IO.lazyPure` around each `Bool`) showed `relsInB` at 10–11 s (each relocation's `tgtOf` scanned every output section's parts, `secsOf`) and `reachOkB` at up to 108 s (`List.lookup` of the link map and the region's size `span sizes` recomputed per referenced name).
- **Trick:** decision variants proven equal to the statements' definitions: `relsInFastB` reads the per-section classification from a `Std.HashMap` built once (`secCls`, `secCls_getD`: its entry is `secsOf`'s answer; `relsInFastB_eq` by `simp` then `rfl`), `reachOkPar` uses `addrMap` and the size computed once (`reachOkPar_eq`, `simp` with `addrMap_get`).
- **Numbers:** the larger fv-demo executable 121,956 ms → 2,889 ms (`relsInB` 10,493 → 88 ms, `reachOkB` 108,454 → 303 ms); the other 17,232 → 1,130 ms (`FV/Link/Ld/RelsFast.lean`, `FV/Link/ExeLdIn.lean`). Same mistake in the link spec's symbol lookups (`symHint`/`firstVals` rebuilt per link-map entry in `inSymsB`/`pinAddr`; fix: `inSymsWith`/`pinAddrWith` taking the tables, built once by `let` outside the `all`/`filterMap`): deps executables (about 20,000 functions) 890–1,321 s → 29–36 s (`specPreB` 254–571 s → 3.8–5.5 s; `FV/Link/Ld/SpecTotal.lean`).

### A table in a lambda is rebuilt per call: bind it with `let` outside
- **Problem:** `link-check --dead-cleanup --prune` on fv-demo with std (28,554 functions) did not finish in 67 min; after the checks (all done in about 4 min) it sat single-threaded in the stack bound. `budMapFast` passed `fun n => (assocMap I.syms)[n]?` to `budSuccFast`, so the 21,057-entry symbol map was rebuilt at every candidate edge of each indirect caller (Lean does not hoist a non-closed term out of a lambda).
- **Trick:** `let sm := assocMap I.syms` before the call, pass `fun n => sm[n]?`; `budMapFast_eq` unchanged (`simp` zeta-reduces). Also one task per function (`Link.parMap`, `parMap_eq`) for the routing recovery's up to five pipelines per function.
- **Numbers:** std bundle link-check >67 min (killed) → 5 min 19 s (stack bound 65 s, max RSS 1.2 GB); same output on 22 non-std executables (`FV/E2E/BinCheckFast.lean`, `FVTest/E2E/LinkCheckMain.lean`).

## From other projects (not yet measured in clifv)

From [Th0rgal/evm.fast-dev](https://github.com/Th0rgal/evm.fast-dev) (`docs/PROOF-PERFORMANCE.md`). All keep ordinary kernel checking and standard axioms. Move an entry up into the sections above once it has been measured here.

- **Kernel-opaque checked caches:** `opaque boxedValue (v : α) : {r : α // r = v} := ⟨v, rfl⟩`, used through its checked equation; full-transparency kernel reduction cannot reopen it. Reported: a 49 GiB timed-out monolith → 3–4 GiB checkpoint certificates. Candidates here: large intermediate states in Stock certificates. Not tried (BuildDiet): after the single-certificate and `AState` changes, the largest module peak is 11.9 GB from one pipeline evaluation, which a cache cannot shrink.
- **Rewrite at the outer boundary:** prove a structural/pure evaluator equal to the executable one once, rewrite at the top, then `rfl`. Unfolding the concrete result and rewriting inside instead was 2× slower (8.8 → 19.9 s).
- **Remove repeated indexing:** proving repeated indexed extraction equal to one linear `flatMap` took a check from an unfinished 5 minutes to 39 s. Measured here, in the form of "one evaluation per certificate" and the List-recursive `AState` traversals above.
- **Compact certificates:** `of_decide_eq_true (by kernel_rfl)` (with `kernel_rfl` = `goal.refl (check := false)`) instead of `decide_cbv` shrank a 30.6 MB `.olean` to 33 KB and halved replay. clifv's `RuleAll` already uses the `check := false` idea.
- **Compact generated data:** typed DAG literals with small single-use nodes inlined shrank 9 MB ASTs to 0.3 MB (61 → 15 s).
